# Implementation

#### Testbed/data

For the first implementation step, I would build a small controlled testbed.

I would generate three types of traffic: ordinary HTTPS traffic, benign DoH traffic to public resolvers, and DoH traffic to private resolvers that I control.

For the private resolver case, I can deploy my own DoH resolver, or use a controlled server-side setup, so that the label is clear.

I would also control the query pattern, for example ordinary queries, low-rate queries, and single-query-like cases.

This gives me a reproducible dataset where I know which flows are DoH, which resolver was used, and under which collection condition the traffic was generated.

---

#### Host window

After collecting packet traces, I would first convert them into flow-level records.

Each flow would have basic metadata, such as packet sizes, directions, timing information, duration, and packet counts.

Then, for each candidate encrypted flow, I would construct a host-level time window around it. The window contains nearby encrypted flows from the same monitored host.

From this window, I would compute context features, such as the number of short flows, timing gaps between flows, repeated size-direction patterns, and the density of low-volume encrypted communication.

So the implementation has two levels: single-flow metadata and host-window metadata.

---

#### Models

I would start with simple baselines before using complex models.

The first baseline is an address-list detector. It checks whether the resolver address is already known. This is useful as a reference, but it cannot handle unseen private resolvers.

The second baseline is a single-flow metadata classifier. It uses only the candidate flow itself.

Then I would implement the host-level model using both the candidate flow metadata and the window-level context features.

At the first stage, I would use simple classifiers, such as logistic regression, random forest, or gradient boosting, because they make the feature contribution easier to inspect.

---

#### Evaluation

For evaluation, I would avoid a random flow-level split.

A random split may put very similar flows from the same resolver or same collection session into both training and test data, which can make the result too optimistic.

Instead, I would split the data by resolver and collection session. For example, some private resolvers would appear only in the test set.

The main evaluation target is whether the host-level model improves detection for short-lived DoH traffic to unseen private resolvers.

I would report detection performance together with false positives, latency, memory use, and processing time.

---

#### Ablation

To understand the result, I would run feature ablation.

I would remove one group of context features at a time, such as short-flow counts, timing gaps, size-direction patterns, or low-volume flow density.

If removing one group clearly reduces performance, that group is likely contributing useful evidence.

If the host-level model does not improve the result, I would check whether the window is too short, too long, or too noisy.

This analysis is important because I do not only want a higher score. I want to know which context information helps and where the method fails.

---

#### Resolver

For the private resolver, I would start with a controlled setup.

For example, I can deploy a DoH-capable resolver on a server or a local virtual machine, using existing software such as DNSdist, or CoreDNS.

The important point is that I control the resolver endpoint, so I know which DoH client queries are sent to that resolver.

This makes the label reliable. I do not need to infer whether the resolver is private from the traffic alone, because the resolver is part of the experimental setup.

---

#### Generation

For traffic generation, I would generate both ordinary HTTPS traffic and DoH traffic.

Ordinary HTTPS traffic can be generated by scripted browser access or command-line clients visiting normal websites.

DoH traffic can be generated by a DoH client, for example using a browser configured to use my resolver, or command-line tools that send DNS queries through HTTPS.

I would control the query frequency to create ordinary DoH, low-rate DoH, and single-query-like cases.

This allows me to test both easier and harder traffic patterns under the same environment.

---

#### Packet capture

For packet capture, I would use standard tools such as Wireshark to collect packet traces.

After capture, I would convert packets into flow records. A flow can be defined by the five-tuple: source IP, destination IP, source port, destination port, and transport protocol.

For each flow, I would extract metadata, then I would group flows by monitored host and construct a time window around each candidate encrypted flow.

---

#### Label

The labels would come from the controlled generation process.

If a flow is generated by my DoH client and sent to the DoH resolver in the experiment, I label it as DoH. Ordinary HTTPS traffic generated by browser or scripted access is labeled as non-DoH.

I would also keep logs from the client or resolver side, so I can match query time and resolver endpoint with the captured traffic.

This is why a controlled testbed is useful: the label does not depend only on guessing from packet features.
